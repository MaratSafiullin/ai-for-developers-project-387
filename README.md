## Сценарий использования

**Владелец**

1. Открывает раздел управления и создаёт тип встречи «Знакомство»: длительность 30 минут, описание «Короткий созвон, чтобы познакомиться и обсудить задачу».
2. Тип встречи появляется в каталоге, доступном гостям.

**Гость**

3. Заходит на сервис без регистрации и открывает каталог типов встреч.
4. Выбирает «Знакомство».
5. Видит календарь на ближайшие 14 дней и выбирает ближайший рабочий день.
6. Из списка свободных слотов выбирает 14:00–14:30.
7. Вводит имя «Анна» и подтверждает запись.
8. Видит экран подтверждения: тип встречи, дата, время 14:00–14:30, имя.

**Владелец**

9. Открывает список предстоящих встреч и видит новую запись: дата, 14:00–14:30, «Знакомство», Анна. Список общий для всех типов встреч и отсортирован по времени, ближайшие сверху.

10. Анна пишет, что не придёт. Владелец нажимает кнопку отмены у её встречи и подтверждает в диалоге. Встреча исчезает из списка, а время 14:00–14:30 снова становится свободным слотом для гостей.

> Занятый слот больше не показывается гостям, в том числе для других типов встреч: интервалы не могут пересекаться даже частично. Следующая встреча может начинаться ровно в момент окончания предыдущей.

### Обязательные функции

- Создание типов встреч с названием, описанием и длительностью
- Каталог типов встреч для гостя
- Календарь свободных слотов на 14 дней вперёд, длительность слота равна длительности типа встречи
- Запись на свободный слот по имени гостя
- Список предстоящих встреч всех типов для владельца
- Запрет пересечения встреч, в том числе разных типов и при одновременных запросах

### Добавлено в этом проекте

- Отмена предстоящей встречи владельцем ([#15](https://github.com/MaratSafiullin/ai-for-developers-project-387/issues/15)): встреча удаляется насовсем, её время снова становится свободным слотом. Начавшуюся или прошедшую встречу отменить нельзя.

### Ограничения

- Нет авторизации и личных кабинетов
- Нет интеграций с внешними календарями и уведомлений, гость не узнаёт об отмене встречи
- Гость не может отменить свою запись, перенести встречу нельзя, нельзя редактировать или удалять типы встреч

## Стек

Проект создан из [Laravel React Starter Kit](https://laravel.com/docs/starter-kits).

- **Бэкенд:** PHP 8.5, Laravel 13, [Inertia](https://inertiajs.com) v3. Страницы рендерятся как React-компоненты через `Inertia::render()`.
- **Фронтенд:** React 19, TypeScript, Tailwind CSS 4, shadcn/ui. Маршруты для фронта генерирует [Wayfinder](https://github.com/laravel/wayfinder).
- **Сборка:** Vite+ (`vp`): сборщик, линтер и форматтер в одном, настраивается в `vite.config.ts`.
- **База данных:** SQLite. Сессии, кеш и очередь хранятся в БД, отдельные сервисы не нужны.
- **Тесты и качество:** Pest, Pint, Larastan (level 7), `tsc`.

## Установка

Нужны PHP 8.5 с Composer и Node.js 22 (версия в `.nvmrc`) с npm.

```bash
git clone https://github.com/MaratSafiullin/ai-for-developers-project-387.git
cd ai-for-developers-project-387
composer setup
```

`composer setup` ставит PHP- и npm-зависимости, подключает git-хуки из `.githooks`, создаёт `.env` из `.env.example`, генерирует ключ приложения, применяет миграции к SQLite, ставит Chromium для e2e-тестов Playwright и собирает фронтенд.

## Проверки и CI

`composer ci:check` — единая команда проверок, локально и в CI:

1. `npm run check`: линтер и форматтер Vite+ (предупреждения считаются ошибками)
2. `npm run contract:check`: OpenAPI и SDK пересобираются из `contract/main.tsp` и совпадают с закоммиченными
3. `npm run types:check`: проверка типов TypeScript
4. `composer lint:check`: стиль PHP (Pint)
5. `composer types:check`: статический анализ PHP (Larastan)
6. `php artisan test`: тесты Pest
7. `npm run test:e2e`: сборка фронтенда и e2e-сценарий в Chromium через Playwright

e2e-тест (`tests/e2e/`) проходит [сценарий использования](#сценарий-использования) против настоящего сервера: владелец создаёт тип «Знакомство», гость выбирает первую дату и первый слот, вводит «Анна» и видит подтверждение, владелец видит встречу в списке предстоящих. Время и дата сверяются с выбранным слотом, а не с фиксированным временем. Перед прогоном Playwright (`playwright.config.ts`) пересоздаёт файл SQLite `database/e2e.sqlite`, применяет к нему миграции без сидера и запускает `php artisan serve` на порту 8010. Рабочая база из `.env` не затрагивается. Конфликты слотов и граничные случаи проверяют тесты Pest, в e2e они не повторяются.

Если Chromium не установлен (например, на клоне, где `composer setup` выполнялся раньше), поставьте его: `npx playwright install chromium`. При падении трейс прогона сохраняется в `test-results/` и открывается командой `npx playwright show-trace <путь к trace.zip>`.

GitHub Actions (`.github/workflows/tests.yml`) на каждый push в `main` и pull request выполняет `composer setup`, ставит системные зависимости Chromium (`npx playwright install --with-deps chromium`) и запускает `composer ci:check`. Параллельно job `docker` собирает Docker-образ, запускает его с `PORT=8080` и ждёт ответа 200 от главной страницы.

Коммиты пишутся по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): тип и scope на английском, описание на русском в инфинитиве, например `feat(api): добавить календарь свободных слотов`. Формат проверяет хук `.githooks/commit-msg`. На клоне, где `composer setup` уже выполнялся до появления хука, подключите его один раз: `git config core.hooksPath .githooks`.

## Релизы

Релизы выпускает [release-please](https://github.com/googleapis/release-please) по истории коммитов, руками версию и CHANGELOG не правят.

1. После каждого push в `main` workflow `.github/workflows/release-please.yml` открывает или обновляет релизный PR `chore(main): release X.Y.Z`. В нём следующая версия и пополненный `CHANGELOG.md`.
2. Версию определяют типы коммитов с прошлого релиза. Пока проект в `0.x`, `feat` поднимает минорную версию, `fix` — патч, ломающее изменение (`!`) — тоже минорную. Первый релиз — `0.1.0`.
3. Когда релизный PR сливают, появляются тег `vX.Y.Z` и GitHub Release с теми же заметками.

В CHANGELOG попадают `feat`, `fix`, `perf`, `revert`, `refactor` и `docs`; `chore`, `ci`, `build`, `test` и `style` скрыты. Настройки лежат в `release-please-config.json`, текущая версия — в `.release-please-manifest.json`.

Релизный PR создаётся встроенным `GITHUB_TOKEN`, поэтому проверки `tests.yml` на нём сами не запускаются. Чтобы workflow мог открывать PR, в настройках репозитория (Settings → Actions → General) должна быть включена опция «Allow GitHub Actions to create and approve pull requests».

## Деплой

Приложение работает на [Render](https://render.com) по адресу https://ai-for-developers-project-387-22vi.onrender.com. Сервис описан в Blueprint `render.yaml`: один web-сервис из `Dockerfile`, бесплатный тариф, регион Frankfurt, проверка здоровья по `/up`.

### Релиз → деплой

1. Сливают релизный PR release-please, появляются тег и GitHub Release.
2. В том же запуске `.github/workflows/release-please.yml` job `deploy` вызывает deploy hook Render с `ref=<SHA релизного коммита>`.
3. Render собирает образ из этого коммита и переключает сервис на него.

Обычные push в `main` сервис не трогают: в `render.yaml` стоит `autoDeployTrigger: off`. Исключение — изменения самого `render.yaml`: Render синхронизирует Blueprint и пересобирает сервис из текущего `main` (в списке деплоев триггер `blueprint_sync`). URL хука хранится в секрете репозитория `RENDER_DEPLOY_HOOK_URL`. Отдельный workflow `on: release` не подходит: релиз создаёт `GITHUB_TOKEN`, а его события не запускают другие workflow.

Первичная настройка, один раз:

1. В дашборде Render: New → Blueprint, выбрать этот репозиторий.
2. Скопировать Deploy Hook из настроек сервиса в секрет репозитория `RENDER_DEPLOY_HOOK_URL` (Settings → Secrets and variables → Actions).

`APP_KEY` генерирует Render (`generateValue`). Он выдаёт голую base64-строку, и entrypoint сам добавляет к ней префикс `base64:`.

### Хранение данных

База — файл SQLite внутри контейнера, постоянного диска нет. Все типы встреч и записи пропадают при каждом деплое, рестарте и засыпании сервиса. Бесплатный сервис засыпает после 15 минут без запросов, поэтому первый запрос после простоя ждёт запуска контейнера, это может занять около минуты.

Сервер — `php artisan serve`, запросы он обрабатывает по одному. Двойное бронирование это не открывает: пересечения отсекает уникальный индекс в БД ([ADR 0002](docs/adr/0002-meeting-cells-unique-index.md)).

### Локальный запуск образа

```bash
docker build -t calendar .
docker run --rm -e PORT=8080 -p 8080:8080 calendar
```

Приложение откроется на http://localhost:8080. При старте `docker-entrypoint.sh` создаёт файл SQLite, применяет миграции и запускает сервер на `$PORT`. Если `APP_KEY` не передан, генерируется временный ключ.

## Разработка с AI-агентами

В проекте установлен [Laravel Boost](https://laravel.com/docs/boost). Он даёт агентам MCP-сервер (документация по версиям пакетов, схема БД, логи), набор skills и файл инструкций `AGENTS.md`.

**`AGENTS.md` и `boost.json` закоммичены, но `AGENTS.md` генерируется, руками его не правят.** Boost собирает его из правил версий установленных пакетов и проектных правил в `.ai/guidelines/`, а `boost.json` хранит настройки генерации: агентов, skills, MCP. По ним файл воспроизводится одной командой.

После клонирования поставьте локальные skills и конфиг MCP:

```bash
php artisan boost:update
```

`php artisan boost:install` нужен, только чтобы поменять агентов или набор skills: он перезапишет `boost.json`, который потом надо закоммитить.

Проектные правила для агентов хранятся в закоммиченном каталоге `.ai/`:

- `.ai/guidelines/*.md`: правила, которые вклеиваются в `AGENTS.md` при генерации
- `.ai/skills/<name>/SKILL.md`: свои skills
- `.ai/rules/`: правила с привязкой к путям

После правки `.ai/guidelines/` запустите `php artisan boost:update`. При `composer update` Boost делает это сам. Обновлённый `AGENTS.md` закоммитьте.

`CLAUDE.md`, `.mcp.json`, `.claude/`, `.junie/` и каталоги других агентов остаются локальными и лежат в `.gitignore`. Исключение — `.claude/settings.json`: это общие правила разрешений Claude Code для проекта, он закоммичен. `CLAUDE.md` не создавайте: при его наличии Boost пишет инструкции туда, а не в `AGENTS.md`.

### Агент в GitHub

Воркфлоу `.github/workflows/claude.yml` запускает Claude Code в GitHub Actions по комментарию в issue или pull request. Агент отвечает комментарием от имени приложения Claude, а правки пушит в ветку.

| Параметр        | Значение                                                                                                                                                                                                                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Событие         | `issue_comment` (обсуждение issue или PR) и `pull_request_review_comment` (комментарий к строке diff), только `types: [created]`: правка комментария агента повторно не зовёт                                                                                                                                                                                |
| Команда         | `@claude` в тексте комментария, значение `trigger_phrase` по умолчанию                                                                                                                                                                                                                                                                                       |
| Кто может звать | автор с `author_association` `OWNER`, `MEMBER` или `COLLABORATOR` и не бот. Остальные комментарии отсекает условие `if` до вызова модели. Экшен вдобавок сам пускает только пользователей с правом записи                                                                                                                                                    |
| Модель          | `claude-sonnet-5-5` (Anthropic API), задаётся в `claude_args --model`                                                                                                                                                                                                                                                                                        |
| Ключ            | секрет репозитория `ANTHROPIC_API_KEY`                                                                                                                                                                                                                                                                                                                       |
| Бюджет в PR     | не больше трёх допущенных запусков агента на PR; при неуспехе задание без модели публикует в PR отчёт с причиной, см. «Бюджет запусков на PR»                                                                                                                                                                                                                |
| Назначение      | ответы на вопросы, спеки (`to-spec`), тикеты (`to-tickets`), правки и реализация спецификации по тикетам (`implement-spec`) по TDD                                                                                                                                                                                                                           |
| Где результат   | ответ — комментарием в том же issue или PR. Правки по поручению в issue — в ветке `claude/...` и в PR, который агент открывает сам от имени `claude[bot]`; правки по поручению в PR — новыми коммитами в ветку этого PR. Журнал прогона — во вкладке [Actions](https://github.com/MaratSafiullin/ai-for-developers-project-387/actions/workflows/claude.yml) |

**Почему Claude Code, а не OpenCode.** Задание предлагает OpenCode и его GitHub App. Здесь подключён тот же агент, что используется локально: Claude Code через официальный экшен [`anthropics/claude-code-action`](https://github.com/anthropics/claude-code-action) и [Claude GitHub App](https://github.com/apps/claude). Сценарии те же: вызов командой из комментария, скиллы проекта, ответ и правки от имени приложения. Соответствие настроек:

- `mentions` у OpenCode — это `trigger_phrase` у Claude. Оставлено значение по умолчанию `@claude`, свои команды не заводились.
- `share` у OpenCode публикует сессию по ссылке. У Claude Code такой публикации нет. Ближайший параметр — `show_full_output`: при `true` весь диалог агента, включая ответы API, печатается в журнал Actions, а в открытом репозитории этот журнал публичный. Решение: `show_full_output: false`, наружу видны только комментарии агента.
- Правила проекта агент берёт из `AGENTS.md`, как и локально. `CLAUDE.md` не нужен (см. выше).

**Скиллы на раннере.** Раннер стартует с чистой машины, поэтому воркфлоу ставит скиллы сам:

- плагин `mattpocock-skills` из каталога `claude-plugins-official` (входы `plugin_marketplaces` и `plugins`) — тот же, что установлен локально: `to-spec`, `to-tickets`, `implement-spec` и остальные;
- проектные скиллы Boost: `composer install` и `php artisan boost:update` генерируют `.claude/skills/`, который не хранится в git.

`to-spec`, `to-tickets` и `implement-spec` помечены `disable-model-invocation: true`: локально их запускает только набранная человеком slash-команда, а модель сама вызвать их не может. В GitHub текст комментария приходит агенту внутри промпта экшена, а не как slash-команда, поэтому такой скилл агент открывает как файл: находит `SKILL.md` в каталоге установленного плагина и выполняет его. Просите прямо, например: `@claude прочитай SKILL.md скилла to-spec из плагина mattpocock-skills и выполни его по обсуждению этого issue`. Скиллы без этой пометки (`tdd`, `code-review`, скиллы Boost) агент вызывает сам.

Настройки трекера (`docs/agents/`) и правила (`AGENTS.md`) приходят вместе с кодом при checkout.

#### Примеры команд

Вопрос по коду. Агент читает файлы и отвечает комментарием, ничего не меняя:

```text
@claude как считается список свободных слотов для записи? Назови файлы и методы, которые в этом участвуют
```

Составление спека через `to-spec`. Скилл нельзя вызвать slash-командой, поэтому просим открыть его `SKILL.md`. Спек агент опубликует в трекер как issue:

```text
@claude прочитай SKILL.md скилла to-spec из плагина mattpocock-skills и выполни его по обсуждению этого issue
```

Мелкая правка. Агент меняет файл в ветке `claude/...` и сам открывает PR:

```text
@claude поправь в README.md опечатку в разделе «Установка» и открой PR
```

Реализация спецификации через `implement-spec`, в issue спецификации. Агент выполняет тикеты по очереди в одной ветке, каждый по TDD, проводит финальное `code-review` и открывает один PR с описанием по шаблону:

```text
@claude прочитай SKILL.md скилла implement-spec из плагина mattpocock-skills и выполни его для этой спецификации и её тикетов
```

**Адаптация `implement-spec` к экшену.** Экшен сам создаёт ветку `claude/...` и не даёт агенту создавать ветки и мержить. Поэтому правила для GitHub, которые воркфлоу добавляет к системному промпту агента (`--append-system-prompt` в `claude_args`), меняют скилл так: ветка экшена служит интеграционной, тикеты выполняются в ней последовательно в порядке графа зависимостей, без worktree, отдельных веток тикетов и merge. Субагенты допускаются. Финальное `code-review` остаётся. Вместо чернового PR скилла агент в конце открывает один готовый PR: черновой авторевью пропускает, а перевести его в готовый агенту нечем. Те же правила требуют работать по TDD, открывать PR самому, заполнять описание по `.github/pull_request_template.md` и на поручение в PR пушить в его ветку, не открывая нового. Ссылку «Create a PR» в итоговый комментарий экшен добавляет сам после работы агента, если в ветке есть изменения, и не проверяет, открыт ли уже PR. Поэтому она может остаться рядом со ссылкой на PR агента. Создавать второй PR по ней не нужно.

**Права.** Права заданы у каждого задания отдельно, на уровне воркфлоу их нет. Задание проверки бюджета получает только `actions: read`, задание отчёта — только `pull-requests: write`; модель ни одно из них не вызывает (см. «Бюджет запусков на PR»). Дальше — о задании агента. Комментарии, push и создание PR делает токен Claude GitHub App: экшен получает его обменом OIDC-токена, поэтому у задания `id-token: write`. PR создаётся через GitHub MCP-сервер экшена (`mcp__github__create_pull_request`), который работает с этим же токеном. Поэтому PR агента, в отличие от PR от `GITHUB_TOKEN`, сразу запускает CI и авторевью, без «Approve workflows to run». Токен воркфлоу (`GITHUB_TOKEN`) получает только `contents: read`, `issues: write` и `pull-requests: read`: он передаётся в `GH_TOKEN`, чтобы `gh` в скиллах трекера мог читать и создавать issues и читать PR. У `actions/checkout` стоит `persist-credentials: false`, экшен сам настраивает push токеном приложения. Агенту разрешены (`claude_args --allowedTools`):

- `Skill`, `Agent` и `Task` (субагенты, прежнее имя инструмента оставлено на всякий случай), `Edit`, `Write`;
- `mcp__github__create_pull_request`;
- `gh issue view|list|create|comment|edit`, `gh pr view|diff` и `gh api`. `gh api` нужен скиллу `to-tickets`, чтобы связывать тикеты как sub-issues и проставлять зависимости «blocked by». За пределы репозитория и прав `GITHUB_TOKEN` он не выходит;
- `git status|diff|log`, а коммит и push экшен разрешает сам;
- `php artisan test`, `php artisan make:*`, `vendor/bin/pint`, `vendor/bin/phpstan`, `npm run contract:generate`, `npm run build`, `npm run check:fix` и `npm run types:check`: тесты по TDD, стиль PHP, статический анализ, генерация контракта и SDK, сборка манифеста Vite и маршрутов Wayfinder, линтер и формат TS/React, проверка типов TS.

Для этого задание ставит PHP-зависимости, Node и npm-зависимости, собирает фронтенд (feature-тестам нужен манифест Vite) и включает `.githooks`, чтобы хук `commit-msg` проверял коммиты агента. Браузерные тесты и полный `composer ci:check` агент не запускает: их выполняет `tests.yml` в PR, как для любой ветки.

**Что видно в журнале.** При `show_full_output: false` экшен не пишет в журнал вызовы инструментов. Поэтому после агента шаг «List Agent Tool Calls» печатает из файла выполнения экшена список вызванных инструментов и команд Bash, без их вывода. По нему видно, какие тесты и проверки запускал агент. Вывод команд в журнал не попадает: в нём могут оказаться секреты, а журнал открытого репозитория публичный.

**Безопасность.** Воркфлоу не использует `pull_request_target`: комментарии из fork не получают ни ключа, ни права записи, потому что их авторы не проходят фильтр `author_association`. Ключ хранится только в секретах. Экшен закреплён хешем коммита, его обновления предлагает Dependabot.

**Остановка и расход.** Тайм-аут 60 минут стоит на шаге агента (`AGENT_TIMEOUT_MINUTES`): `implement-spec` выполняет несколько тикетов по TDD и финальное ревью. Значение по умолчанию меняет переменная репозитория `AGENT_TIMEOUT_MINUTES` (Settings → Secrets and variables → Actions → Variables), целое число минут меньше тайм-аута задания. Например, `1` позволяет проверить отчёт `timeout`; после проверки переменную удаляют. Переменная нужна потому, что экшен отказывается работать, если `claude.yml` отличается от версии в `main`, и попробовать другое значение в ветке PR нельзя. Тайм-аут задания, 80 минут, оставляет запас на подготовку и ловит только её зависание. `concurrency` по номеру issue или PR ставит повторный вызов в очередь, а не запускает его параллельно. В PR в очередь встаёт весь прогон, от проверки бюджета до отчёта. GitHub держит в группе только один ожидающий прогон: если, пока агент работает, пришли два вызова подряд, более ранний ожидающий отменяется до старта, бюджет не расходует и отчёта не оставляет. Расход на PR ограничивает бюджет запусков, см. ниже. Текущий прогон останавливает Cancel workflow на странице прогона, будущие — Disable workflow во вкладке Actions. Уже отправленный запрос к API может доработать на стороне Anthropic; в крайнем случае ключ отзывается в [Console](https://console.anthropic.com/settings/keys).

**Первичная настройка**, один раз:

1. Установить [Claude GitHub App](https://github.com/apps/claude) на этот репозиторий. Команду `/install-github-app` из Claude Code не используйте: она создаёт свой воркфлоу и PR, которые конфликтуют с `claude.yml`.
2. Добавить ключ Anthropic API в секрет `ANTHROPIC_API_KEY` (Settings → Secrets and variables → Actions).

#### Бюджет запусков на PR

На один pull request агент запускается не больше трёх раз (`RUN_LIMIT` в задании `budget`). Бюджет проверяется до вызова модели, поэтому отказ ничего не стоит.

| Что                         | Расходует бюджет                                                |
| --------------------------- | --------------------------------------------------------------- |
| Вызов агента в PR           | да, и из общего комментария, и из комментария к строке diff     |
| Попытка допущенного прогона | да, каждая: успех, ошибка, отмена, тайм-аут и Re-run            |
| Недоверенный комментарий    | нет: прогон отсекает фильтр автора, задание агента пропускается |
| Отказ по бюджету            | нет                                                             |
| Авторевью и вызовы в issue  | нет, бюджет есть только у вызовов агента в PR                   |
| Прогоны других PR           | нет: у каждого PR свой счётчик, новый PR начинает с нуля        |

**Как считается.** Номер PR вписан в имя прогона (`run-name`): `claude: PR #N`, у вызовов в issue — `claude: issue #N`. Задание `budget` без модели запрашивает через Actions API прогоны `claude.yml` с этим именем, созданные не раньше PR, и задания всех их попыток (`filter=all`). Допущенной считается попытка, в которой проверка бюджета прошла успешно, а задание агента `claude` не было пропущено. Текущая попытка не считается. Если допущенных попыток меньше трёх, агент стартует, иначе задание агента пропускается. Счётчик хранится в истории Actions, а не в комментариях: ни агент, ни правка комментария его не меняют. Чтобы два вызова не прошли проверку одновременно, прогоны вызовов в одном PR идут строго по очереди (`concurrency` уровня воркфлоу).

**Re-run.** Перезапускайте прогон целиком, «Re-run all jobs»: это новая попытка, бюджет проверяется заново и расходуется. «Re-run failed jobs» не перезапускает успешную проверку бюджета, поэтому задание агента в такой попытке пропускается, а отчёт называет причину `infra`.

**Отчёт.** Задание `report` без модели запускается после задания агента при любом исходе. Если агент отработал успешно, отчёта нет: агент отвечает сам. Иначе в PR появляется комментарий «Агент остановлен» с причиной, последним SHA ветки PR, ссылкой на журнал прогона и статусом «нужен человек».

| Причина           | Когда                                                                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `limit_exhausted` | бюджет PR исчерпан, модель не вызывалась                                                                                                      |
| `timeout`         | шаг агента остановлен тайм-аутом шага. Тайм-аут отличается от отмены по прошедшему времени шага                                               |
| `infra`           | не прошла проверка бюджета или подготовка задания агента: установка зависимостей, сборка, нет секрета `ANTHROPIC_API_KEY`; Re-run failed jobs |
| `agent_failed`    | шаг агента завершился ошибкой или прогон отменили вручную                                                                                     |

**Ограничения.** Бюджет держится, пока сохранена история Actions и не изменена конфигурация воркфлоу: удалённые прогоны из счётчика выпадают, а правка `claude.yml` меняет сами правила. Администратор репозитория может обойти бюджет, например удалив прогоны или отключив проверку. Вызов из общего комментария идёт по `claude.yml` из `main`, а вызов из комментария к строке diff — по `claude.yml` из ветки PR. Если в ветке PR `claude.yml` изменён, экшен агента сверяет его с `main`, отказывается работать и модель не вызывает, поэтому обойти бюджет правкой воркфлоу в PR нельзя. Такой прогон при этом расходует попытку и завершается успешно без ответа агента: причина видна только в журнале шага Run Claude («Workflow validation failed»). Прогоны, созданные до появления бюджета, называются иначе и не считаются.

#### Автотриаж

Воркфлоу `.github/workflows/triage.yml` делает предварительный разбор каждого нового обращения без комментария `@claude`. Агент читает `AGENTS.md`, `GLOSSARY.md` и `docs/agents/`, открывает `SKILL.md` скилла `triage` и разбирает issue с учётом текущего приложения. Результат — один комментарий с Triage Notes и вопросами, метка категории и метка состояния: `needs-info`, если данных не хватает, иначе `needs-triage`. Дальше решает человек: ответить, позвать `@claude` или взять задачу в работу.

| Параметр         | Значение                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Событие          | `issues`, только `types: [opened]`: правка issue разбор не повторяет                                                                                                                                                                                                                                                                                                                                                                                     |
| Кто запускает    | автор issue с `author_association` `OWNER`, `MEMBER` или `COLLABORATOR` и не бот. Остальные запуски условие `if` пропускает до вызова модели                                                                                                                                                                                                                                                                                                             |
| Что пропускается | issue, созданные с меткой `ready-for-agent` или `ready-for-human`: это спецификации и тикеты от `to-spec` и `to-tickets`, они уже готовы к реализации. Метки взяты из `docs/agents/triage-labels.md`. Такой запуск в Actions завершается со статусом skipped. Если метку поставили сразу после создания, а не в самом `gh issue create`, её не будет в событии `opened`, поэтому агент первым делом перечитывает метки и при `ready-*` молча завершается |
| Prompt           | задан в воркфлоу, а не в комментарии. В него попадают только имя репозитория и номер issue, текст обращения агент читает сам через `gh issue view`, поэтому содержимое issue не становится частью инструкции                                                                                                                                                                                                                                             |
| Ограничения      | код не меняет и не пушит, issue не закрывает, `wontfix` и `ready-for-agent` не ставит: это решения человека                                                                                                                                                                                                                                                                                                                                              |
| Тайм-аут         | `timeout-minutes: 10`                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Параллельность   | `concurrency` с одной группой `triage` на весь репозиторий: одновременно идёт не больше одного разбора. GitHub держит в группе только один ожидающий запуск, поэтому при всплеске обращений более ранний ожидающий отменяется. Такое issue разбирают вручную через `@claude`                                                                                                                                                                             |
| Модель и ключ    | те же, что у `claude.yml`: `claude-sonnet-5-5` и секрет `ANTHROPIC_API_KEY`                                                                                                                                                                                                                                                                                                                                                                              |

**Права.** У задания `contents: read`, `issues: write` и `id-token: write`. Агенту разрешены только `Skill`, `Read`, `Glob`, `Grep` и формы `gh issue view|list|comment|edit`: без `Edit`, `Write` и `gh api`. Инструменты чтения перечислены явно: в режиме `prompt` экшен, в отличие от режима упоминания, сам их не добавляет, а без `Read` агент не открывает `SKILL.md` скилла `triage` из каталога плагина. PHP, composer и `boost:update` не ставятся: разбор не пишет код, а правила проекта приходят из закоммиченного `AGENTS.md`.
**Тикеты от агента.** Спецификации и тикеты, которые агент публикует по `@claude`, создаются от имени приложения `app/claude`. Они запускают `triage.yml`, но запуск пропускается условием «не бот» и метками. Спецификации и тикеты из локальной сессии создаются от имени человека, их отсекают метки `ready-*`.

#### Авторевью

Воркфлоу `.github/workflows/auto-review.yml` автоматически ревьюит каждый pull request. Ревьюер читает описание PR, связанные спецификацию, тикеты и согласование, diff PR и отдельных коммитов, результаты CI, если они уже есть, и прошлые комментарии PR, включая прежние авторевью. Результат — новый комментарий в PR с заголовком «Авторевью» и SHA проверенного коммита. Код ревьюер не меняет, правки по замечаниям вносит агент по команде `@claude` от мейнтейнера.

| Параметр       | Значение                                                                                                                                                                                                                                                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Событие        | `pull_request` с типами `opened`, `synchronize`, `reopened`, `ready_for_review`. Черновик не ревьюится, перевод в готовый запускает ревью. `pull_request_target` не используется                                                                                                                                                                                     |
| Допуск         | head-ветка PR в этом репозитории, а автор PR — `OWNER`, `MEMBER`, `COLLABORATOR` или `claude[bot]`. PR из fork, от других авторов и от прочих ботов пропускаются условием `if` и не получают секрет модели                                                                                                                                                           |
| Запуск модели  | голый CLI Claude Code (`claude -p`, версия закреплена в воркфлоу), а не `claude-code-action`: экшен отклоняет события от бота, а push Claude App в ветку PR — как раз такое событие                                                                                                                                                                                  |
| Модель и ключ  | `claude-sonnet-5-5` и секрет `ANTHROPIC_API_KEY`, ключ передаётся только шагу ревью                                                                                                                                                                                                                                                                                  |
| Критерии       | `REVIEW.md` из базовой ветки PR, встраивается в запрос текстом. PR не может ослабить собственное ревью. Если в базовой ветке файла нет, ревью идёт без критериев, и комментарий об этом предупреждает                                                                                                                                                                |
| Тайм-аут       | `timeout-minutes: 15` у задания ревью, 5 минут у публикации                                                                                                                                                                                                                                                                                                          |
| Параллельность | `concurrency` по номеру PR с `cancel-in-progress: true`: новый push отменяет идущее ревью прежнего коммита и запускает новое                                                                                                                                                                                                                                         |
| Сбой           | если CLI вернул ошибку, упёрся в лимит, дал пустой ответ или ревьюер не смог прочитать diff и ответил `REVIEW-BLOCKED`, задание ревью падает и комментарий не публикуется. Причина и отклонённые вызовы инструментов видны в журнале прогона во вкладке [Actions](https://github.com/MaratSafiullin/ai-for-developers-project-387/actions/workflows/auto-review.yml) |

**Права.** Воркфлоу состоит из двух заданий. Задание ревью получает только права на чтение (`contents`, `issues`, `actions`, `checks`, `statuses`, `pull-requests`) и секрет модели. Модели доступны только `Read`, `Glob`, `Grep` и `Bash`, причём из команд разрешены `gh pr view|diff|checks`, `gh issue view`, `gh run list|view`, `gh api` для комментариев к строкам diff этого PR, `git show|log|diff` и встроенные команды только для чтения. Checkout делается с полной историей (`fetch-depth: 0`), поэтому ревьюер видит изменения каждого коммита PR, а не только общий diff против базы, и по ним проверяет правки после прошлого авторевью. Остальные команды требуют подтверждения, а в неинтерактивном запуске подтвердить их некому, поэтому они отклоняются. Записать через `gh` ревьюер ничего не может: у токена нет прав на запись. Запушить через `git` тоже: checkout не сохраняет учётные данные (`persist-credentials: false`), а `git push` не разрешён. `--bare` и `--setting-sources user` не дают ветке PR подложить свои хуки, настройки, плагины и MCP-серверы из `.claude/`. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` убирает ключ модели из окружения команд, которые запускает модель, и принудительно включает песочницу Bash в Claude Code. Для неё задание ставит `bubblewrap` и `socat` и заменяет штатный профиль AppArmor `bwrap-userns-restrict` профилем из документации Claude Code: штатный запрещает песочнице user namespaces, а раннер одноразовый. До вызова модели задание проверяет, что вложенный user namespace внутри `bwrap` создаётся, иначе падает и выводит отказы AppArmor. Песочница пускает команды в сеть только к `api.github.com`, не выпускает их из себя (`allowUnsandboxedCommands: false`), а если не может запуститься, останавливает ревью (`failIfUnavailable: true`). Текст ревью передаётся артефактом во второе задание. Оно не вызывает модель, получает `pull-requests: write`, добавляет заголовок с SHA и ссылкой на прогон и публикует комментарий через `gh pr comment`. OIDC не используется.

**Что ревьюер не видит.** Авторевью идёт параллельно с CI, поэтому результатов CI и артефакта браузерной проверки на момент ревью может ещё не быть, тогда ревьюер так и пишет. Перед мержем мейнтейнер сам сверяет SHA артефакта с head PR. Если авторевью не стартовало на PR агента, проверьте, каким токеном создан PR: события от `GITHUB_TOKEN` воркфлоу не запускают.

#### Аудит производительности

Воркфлоу `.github/workflows/perf-audit.yml` раз в неделю проверяет скорость гостевых страниц работающего приложения. Это единственная работа агента, которая идёт по расписанию, без комментария или нового issue. Lighthouse CI снимает отчёт, шаг без модели сжимает его в сводку, а агент сверяет находки с уже заведёнными задачами. По новой проблеме он заводит issue, а вердикт каждого запуска пишет в журнал аудита.

| Параметр       | Значение                                                                                                                                                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| События        | `schedule` и `workflow_dispatch` в одном файле: ручной запуск проверяет ровно то, что выполняется по расписанию                                                                                                                          |
| Расписание     | `cron: '17 6 * * 1'` с `timezone: Europe/Moscow`, понедельник 06:17 МСК. Минута 17 уводит запуск с пиковой нагрузки начала часа. Деплои идут только по релизу, поэтому ежедневный замер почти всегда повторял бы прошлый                 |
| Адрес          | переменная репозитория `APP_URL` (Settings → Secrets and variables → Actions → Variables). Перед замером воркфлоу до 3 минут ждёт ответа 200 от `$APP_URL/up`, чтобы холодный старт бесплатного Render не попал в отчёт                  |
| Страницы       | `/` и `/book`, по три прогона Lighthouse на страницу, только категория Performance, мобильный пресет по умолчанию. Lighthouse CI закреплён версией (`npx @lhci/cli@0.16.0`), `package.json` не меняется                                  |
| Находка        | см. «Критерии находки» ниже                                                                                                                                                                                                              |
| Режимы         | input `report` у ручного запуска: `live` (по умолчанию) или `training`. Расписание всегда идёт в `live`                                                                                                                                  |
| Тайм-аут       | `timeout-minutes: 20` у задания, 10 минут у шага агента                                                                                                                                                                                  |
| Параллельность | `concurrency` с группой `perf-audit` без отмены идущего прогона: два аудита не идут одновременно и не заводят одну находку дважды. GitHub держит в группе только один ожидающий запуск                                                   |
| Модель и ключ  | `claude-sonnet-5-5` через `claude-code-action` в режиме `prompt`, секрет `ANTHROPIC_API_KEY`, `show_full_output: false`. Промпт задан в воркфлоу: в нём только режим, ссылка на прогон и путь к сводке, данные агент читает из файла сам |

**Где результаты.**

- Артефакт прогона `perf-audit-live` или `perf-audit-training`: каталог `.audit/` с конфигом и отчётами Lighthouse CI (`.lighthouseci/lhr-*.json` и `.html`) и сводкой `summary.json`. Загружается при любом исходе. Каталог `.audit/` лежит в `.gitignore`, отчёты в коммиты не попадают.
- Журнал аудита — закрытое issue «Журнал аудита производительности» с маркером `<!-- perf-audit-log -->`. Его создаёт агент при первом запуске, если журнала ещё нет, и пишет об этом в вердикте. Закрывает журнал мейнтейнер вручную один раз, чтобы служебная запись не висела среди открытых: права закрывать issues у агента нет. Дальше агент находит журнал по маркеру в любом состоянии. В теле секция «Последний запуск» с двумя строками, живой и учебной: дата, прогон, адрес, вердикт и issues находок. Она обновляется при каждом запуске. Новый комментарий в журнале появляется, только когда меняется набор находок или вердикт своего режима или находка вернулась, поэтому одинаковые недели журнал не засоряют. Журнал хранится дольше артефакта.
- Summary прогона: тот же вердикт. Агенту нечем писать файлы, поэтому его последний ответ копирует в `GITHUB_STEP_SUMMARY` шаг без модели. Тот же шаг печатает в журнал прогона список вызванных команд `gh` и отклонённых вызовов, без их вывода.

**Тексты issues и комментариев** агент передаёт в `gh` через стандартный ввод: `--body-file - <<'EOF'`. Многострочный `--body '...'` Claude Code отклоняет, и в одном из первых прогонов из-за этого не обновилось тело журнала. Промпт требует heredoc для всех текстов.

**Сводка.** Агенту передаётся не полный JSON Lighthouse, а сжатая сводка: аудит дешевле, а вывод воспроизводим. Её собирает `jq`-скрипт `.github/perf-audit/summary.jq`: режим, статус, проверенный адрес, SHA `main`, медианы LCP, CLS и TBT по страницам и находки. Значение каждой страницы — медиана трёх прогонов, поэтому разброс одного прогона находкой не становится.

**Критерии находки.** Критерий явный, не на усмотрение модели:

- `lighthouse/<audit-id>` — аудит категории Performance с медианным score ниже 0.9 хотя бы на одной странице. Аудиты без оценки (informative, notApplicable, manual, error) и скрытые в отчёте не считаются. Метрики FCP и Speed Index проверяются здесь по score, а LCP, CLS и TBT — отдельно, по порогам ниже;
- `metric/<lcp|cls|tbt>` — метрика хуже порога «good» Core Web Vitals: LCP > 2.5 с, CLS > 0.1, TBT > 200 мс. TBT стоит вместо INP, которого в лабораторном замере нет.

**Дубли.** Ключ находки агент вписывает в тело issue машинным маркером `<!-- perf-audit: <ключ> -->` и ищет задачу по точному совпадению маркера, а не по похожести заголовка.

- Задачи нет — новый issue: проблема, страницы и значения, предлагаемое действие, проверенный адрес и SHA, ссылки на прогон и журнал. Метки `needs-triage` и `performance`, `ready-for-agent` агент не ставит никогда: брать ли задачу в работу, решает мейнтейнер.
- Открытая задача есть, сведения не изменились — агент ничего не пишет. Сравнивает он с последним комментарием аудита в задаче, а если его нет — с её телом, поэтому одно и то же изменение не повторяется каждую неделю.
- Открытая задача есть, а страницы или значения заметно изменились — один комментарий только с изменениями.
- **Отклонённая находка.** Маркер есть только у закрытых issues, и последнее закрытое из них помечено `wontfix` — мейнтейнер решил проблему не исправлять. Агент не пишет в задачу и не заводит новую, а в журнале и вердикте ставит ссылку на закрытый issue с пометкой «(отклонена)». Чтобы находка снова заводилась, достаточно снять метку `wontfix`. Причины отказов собраны в `.out-of-scope/`.
- **Повторное появление.** Маркер есть только у закрытого issue без метки `wontfix` — значит, проблема вернулась. Агент создаёт новый issue со ссылками на закрытый и на закрывший его PR. Если issue закрыли вручную, без PR, агент так и пишет. Если прочитать закрывший PR не удалось, агент пишет и это, с текстом ошибки. Закрытый issue он не переоткрывает. В журнале такая находка отмечена «(вернулась)» в строке последнего запуска и всегда даёт новый комментарий, даже если набор ключей не изменился.

**Нет данных.** Пустой `APP_URL`, `/up` без ответа 200 за 3 минуты, сбой Lighthouse CI или пустой отчёт дают в сводке статус `no-data` с причиной. Это не «находок нет»: отсутствие данных не подтверждает, что проблем нет. Агент всё равно запускается и пишет в журнал и summary «нет данных, это не подтверждает исправление» с причиной, но issues находок не создаёт и не комментирует: недоступность не должна выглядеть ни новой проблемой, ни исправлением. Затем последний шаг завершает прогон ошибкой, чтобы сбой был виден во вкладке Actions. Артефакт со сводкой загружается и в этом случае. Переход в «нет данных» и обратно меняет вердикт и даёт новый комментарий в журнале.

**Учебный режим.** Создание issue показывается на явно учебных данных, если живое приложение находок не даст. В режиме `training` замер не идёт: сводкой служит закоммиченный файл `.github/perf-audit/training-summary.json` того же формата с одной находкой `training/largest-contentful-paint`. Это подготовленные входные данные для демонстрации, а не отчёт запуска, поэтому правилу «отчёты не попадают в коммиты» он не противоречит. Учебный issue получает префикс «[Учебный]» в заголовке, метку `training` и строку о том, что это не подтверждённый дефект приложения. Учебный ключ проходит ту же проверку дублей и повторного появления, что и живой: повторный учебный запуск при открытом учебном issue дубля не создаёт, а после закрытия учебного issue следующий учебный запуск создаёт новый со ссылкой на закрытый. В журнале учебные записи помечены «Учебный запуск, данные из учебной сводки», а учебная строка «Последнего запуска» не перекрывает живую.

**Права.** У задания `contents: read`, `id-token: write` (токен Claude GitHub App через OIDC для экшена), `issues: write` и `pull-requests: read`. Экшен передаёт токен приложения и в `gh` агента, поэтому issues и комментарии аудита идут от `app/claude`. `GITHUB_TOKEN` в `GH_TOKEN` остаётся запасным, его права ограничены теми же `issues: write` и `pull-requests: read`. Записи в код и в PR нет. `pull-requests: read` добавлен сверх спецификации: без него `gh issue view --json closedByPullRequestsReferences` может не прочитать PR, закрывший прежнюю задачу, при повторном появлении находки. Инструментов `gh pr` у агента нет. Агенту разрешены только `Read` и формы `gh issue list|view|create|comment|edit` и `gh label list`, без `Edit`, `Write` и `gh api`: регулярный запуск без присмотра ограничен трекером. Закрывать и переоткрывать issues агент не может. Метки `performance` и `training` мейнтейнер создаёт заранее, агент их только назначает.

**Автотриаж пропускает issues аудита.** Их создаёт приложение Claude (`app/claude`), поэтому `triage.yml` запускается, но условие «автор не бот» пропускает задание до вызова модели: в Actions такие запуски видны со статусом skipped. Так и задумано: агент сам ставит `needs-triage` и даёт в issue достаточно данных для разбора.

**Ручной запуск и отключение.** Actions → perf-audit → Run workflow, ветка `main`, режим `live` или `training`. Из консоли: `gh workflow run perf-audit.yml -f report=training`. Расписание работает только с файлом из `main` и может задерживаться или пропускаться, а в публичном репозитории GitHub отключает его после 60 дней без активности. Будущие запуски отключает `gh workflow disable perf-audit.yml` или Disable workflow во вкладке Actions, включает обратно `gh workflow enable perf-audit.yml`.

### Выводы о работе агентов

В репозитории четыре сценария агента в GitHub: вызов `@claude` из комментария (`claude.yml`), автотриаж (`triage.yml`), авторевью (`auto-review.yml`) и еженедельный аудит производительности (`perf-audit.yml`). Ниже — что пришлось уточнять и менять по ходу.

**Права и инструменты — главный источник итераций.** Почти каждый сценарий заработал не с первого раза из-за того, что агенту не хватало разрешённой команды или права токена: `gh pr view` для чтения PR, `gh api` для связей тикетов, `Read` для `SKILL.md` вне checkout (в режиме `prompt` экшен сам инструменты не добавляет), `--json` у `gh issue view` (обычная форма просит данные проектов, которые токену недоступны), доступ к сохранённому длинному выводу команд. В неинтерактивном запуске отклонённая команда не видна, поэтому со временем каждый воркфлоу стал печатать в журнал прогона вызванные и отклонённые команды. Без этого причину сбоя приходилось угадывать.

**Мягкие запреты в промпте не держат.** Агент пропускал команды сбора контекста, которые ревьюеру велено выполнить, пробовал свои фильтры `--jq` вместо заданной команды, писал тексты многострочным `--body '...'`, который Claude Code отклоняет, и из-за этого журнал аудита не обновлялся. Работает только жёсткая граница: список разрешённых инструментов, права токена, песочница. Там, где без промпта не обойтись, помогает дать точную рабочую форму команды, а не описание.

**Токены и события GitHub.** События от `GITHUB_TOKEN` не запускают другие воркфлоу, поэтому PR агента открывается через MCP-сервер экшена токеном Claude App, иначе на нём не стартуют CI и авторевью. Экшен отклоняет события от бота, поэтому авторевью идёт через голый CLI, а не через `claude-code-action`. В аудите оказалось наоборот: спецификация считала, что issues создаёт `GITHUB_TOKEN`, а экшен передаёт в `gh` токен приложения, и issues идут от `app/claude`. Итог (автотриаж их не разбирает) совпал, но по другой причине: срабатывает фильтр «автор не бот».

**Воркфлоу нельзя проверить до `main`.** Экшен отказывается работать, если `claude.yml` в ветке отличается от `main`, а `workflow_dispatch` и `schedule` берут файл из `main`. Поэтому тайм-аут агента вынесен в переменную репозитория, а логику аудита до мержа я проверял, запуская шаги локально на настоящих отчётах Lighthouse. Окончательная проверка — только живые запуски, и они нашли то, чего не видно в коде.

**Песочница ревьюера.** Изоляция команд ревьюера через bubblewrap потребовала нескольких итераций: штатный профиль AppArmor в Ubuntu запрещает вложенные user namespaces, пришлось заменить его и проверять песочницу до вызова модели, чтобы не платить за заведомо сломанный прогон.

**Расход и остановка.** Бюджет — не больше трёх запусков агента на PR. Он считается по истории Actions, а не по комментариям, которые агент мог бы изменить. У каждого сценария свои тайм-ауты и `concurrency`. Отдельно пришлось описать пограничные случаи: Re-run failed jobs, построчные комментарии, которые идут по `claude.yml` из ветки PR.

**Что менялось в постановке задачи.**

- Скиллы с `disable-model-invocation` в GitHub не вызываются slash-командой: агенту приходится явно поручать открыть их `SKILL.md`. `implement-spec` адаптирован к экшену: одна ветка, без worktree, один готовый PR в конце.
- Автотриаж сначала разбирал готовые тикеты: метка `ready-*` ставилась уже после события `opened`. Теперь агент первым делом перечитывает метки.
- Аудиту не дали права закрывать issues: журнал закрывается вручную один раз. Зато добавили `pull-requests: read`, чтобы он видел PR, закрывший прежнюю задачу.
- Требование ссылок на проверочные прогоны в README появилось при составлении спецификации, а в задании его нет. Его сняли.

**Общий вывод.** Агент хорошо справляется с содержательной частью: разбирает обращения, пишет ревью и тексты issues, сам замечает опечатку в адресе. Почти все проблемы были в обвязке: права, события, формы команд, наблюдаемость. Спецификация, написанная до первого запуска, в таких местах ошибалась, и исправлять её приходилось по результатам живых прогонов.

### MCP Render

Сервисом на Render можно управлять из Claude Code через официальный плагин `render@claude-plugins-official`: смотреть деплои, логи и метрики. Ключей и токенов в репозитории нет, вход идёт через OAuth:

1. Установите плагин: `/plugin install render@claude-plugins-official`, затем перезапустите Claude Code в проекте. Строка `"enabledPlugins": { "render@claude-plugins-official": true }` в закоммиченном `.claude/settings.json` включает плагин для проекта, но сама его не устанавливает и не предлагает установить.
2. Выполните `/mcp`, выберите сервер `render` и пройдите вход в браузере под своим аккаунтом Render.
3. Попросите агента, например: «покажи последние деплои сервиса ai-for-developers-project-387». При первом обращении он спросит, какое рабочее пространство Render использовать: выберите то, где создан сервис.
